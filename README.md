# Vault Ledger

A transaction-safe banking ledger system built with **Java 21, Spring Boot, PostgreSQL, and Flyway**.

Vault Ledger models account balances through an **append-only transaction ledger** rather than storing a mutable balance on the account itself. Deposits, withdrawals, transfers, and initial deposits are recorded as double-entry transactions.

## Features

- User registration and JWT-based authentication
- Role-based authorization with `USER`, `ADMIN`, and `SYSTEM` roles
- Account creation with optional initial deposit
- Deposit and withdrawal operations
- Account-to-account transfers
- Double-entry transaction records
- Append-only transaction history
- Balance calculation from transaction entries
- Pessimistic locking for balance-changing operations
- Deterministic account locking for transfers to reduce deadlock risk
- Account ownership checks
- Account closure only when the balance is zero
- Paginated transaction history
- Transaction history filtering by:
    - Date range
    - Amount range
    - Transaction type
- Sorting transaction history by supported fields
- Request validation
- Centralized exception handling
- Flyway database migrations
- PostgreSQL
- Docker Compose setup
- OpenAPI / Swagger documentation

## Ledger Model

Vault Ledger does not store the current account balance as a mutable field on the `Account` entity.

Instead, the balance is calculated from the account's transaction entries:

```text
Balance = Total Credits - Total Debits
```

Each transaction creates a `TransactionHeader` and two corresponding `TransactionEntry` records.

For example, a transfer:

```text
TransactionHeader
       │
       ├── DEBIT  → Source Account
       │
       └── CREDIT → Destination Account
```

Both entries contain the same transaction amount and belong to the same transaction header.

### Transaction Types

The application currently supports:

- `INITIAL_DEPOSIT`
- `DEPOSIT`
- `WITHDRAWAL`
- `TRANSFER`

### Entry Directions

Each transaction entry is either:

- `CREDIT`
- `DEBIT`

---

## System Vault Account

The application creates a system account during startup if it does not already exist.

```text
Account Number:
SYS-VAULT-0000
```

The system vault is used as the other side of deposits and withdrawals.

For example, a deposit creates:

```text
System Vault     → DEBIT
User Account     → CREDIT
```

A withdrawal creates:

```text
User Account     → DEBIT
System Vault     → CREDIT
```

This keeps these operations represented using the same double-entry transaction model.

---

## Account Creation

During registration, a user account is created together with the application user.

If an initial deposit is supplied, the application creates an `INITIAL_DEPOSIT` double-entry transaction between the system vault and the new account.

Account numbers are generated by the application and checked for collisions before being assigned.

---

## Transfers

Transfers require both the source and destination accounts to be active.

The source account must also have sufficient balance.

Both accounts are acquired using pessimistic write locks.

To reduce the possibility of deadlocks when two concurrent transfers involve the same accounts, the accounts are locked in deterministic order based on their account numbers.

For example:

```text
Account A ──┐
            ├── acquire locks in deterministic order
Account B ──┘
```

The transfer then creates:

```text
Source Account      → DEBIT
Destination Account → CREDIT
```

as entries belonging to the same transaction header.

---

## Account Closure

An account can only be closed when:

1. The account exists and belongs to the authenticated user.
2. The account is currently `ACTIVE`.
3. Its calculated balance is exactly zero.

The account status is then changed to:

```text
CLOSED
```

## Authentication & Authorization

The application uses stateless JWT authentication.

Authentication endpoints are available under:

```text
/auth/**
```

The JWT contains the authenticated username and is validated by `JwtFilter`.

The authenticated user's role is converted into a Spring Security authority:

```text
ROLE_USER
ROLE_ADMIN
ROLE_SYSTEM
```

### Access Control

Most application endpoints require authentication.

The `/accounts/all` endpoint is restricted to:

```text
ADMIN
SYSTEM
```

Users accessing their own accounts are additionally checked through the authenticated username.

---

## Password Security

Passwords are encoded using BCrypt.

The configured password encoder uses BCrypt strength `12`.

JWT authentication uses a configured signing secret and expiration period.

## Balance Calculation

Individual account balances are calculated using a database aggregate query.

Conceptually:

```sql
SUM(
    CASE
        WHEN entry_direction = 'CREDIT'
            THEN amount
        ELSE -amount
    END
)
```

For multiple accounts, the application also provides a grouped balance query and maps the results through `AccountBalanceProjection`.

This allows the account listing operation to retrieve balances using a batch query rather than calculating each account balance independently.

---

## Concurrency Control

Balance-changing operations use database transactions and pessimistic locking.

### Withdrawal

The user's account is locked before checking its balance and creating the withdrawal entries.

### Transfer

Both participating accounts are locked before checking the source balance and creating the transfer entries.

The locking order is deterministic based on account number.

This is intended to prevent concurrent operations from modifying the same account balance state without synchronization.

## Design Summary

The main design decisions in Vault Ledger are centered around representing monetary operations as ledger entries.

Instead of directly updating a balance field:

```text
Deposit
   ↓
Create transaction header
   ↓
Create CREDIT entry
   ↓
Create corresponding DEBIT entry
   ↓
Balance calculated from entries
```

Withdrawals and transfers follow the same double-entry approach.

Concurrency-sensitive operations use database locking, while account ownership is checked against the authenticated user.

This keeps account balance changes represented by transaction records rather than mutable balance state.
